# CI con GitHub Actions

**Objetivo.** Ver cómo GitHub ejecuta el lint y las pruebas en cada pull request, en Ubuntu y en Windows. Rompes una prueba a propósito en una rama, ves el check en rojo, la arreglas y ves el verde.
Al final sabes leer un check fallido y cómo evitar que un cambio llegue a `main` sin pasar las pruebas.

**Problema del prototipo que trata.** Ninguno de los nueve en particular. CI protege las correcciones de las guías 02 a 04. Si alguien relaja el contrato de datos o rompe el gate, una prueba falla antes del merge y no después, en producción.

Necesitas tu propio repositorio en GitHub, creado desde la plantilla en la [preparación](00-preparacion.md). Si nunca usaste CI, lee antes el primer [CI/CD](../primers/03-ci-cd.md). Las salidas de GitHub salen del repositorio del instructor (`AHuaman/demo-mlops`); en las tuyas cambian el usuario, los números de PR y los ids.

## Paso 1. Recorre el workflow

El workflow vive en `.github/workflows/ci.yml`. Ábrelo. Empieza por los eventos que lo disparan:

```yaml
on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:
```

Corre en cada push a `main`, en cada pull request y cuando lo lanzas a mano desde la pestaña **Actions** (`workflow_dispatch`). Un push a otra rama, sin pull request, no lo dispara.

El primer job, `test`, repite en una máquina limpia lo que harías tú:

```yaml
  test:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.3.3
        with:
          enable-cache: true
      - run: uv sync --locked --all-extras
      - run: uv run ruff check
      - run: uv run ruff format --check
      - run: uv run pytest
```

- `matrix` ejecuta el mismo job dos veces, una en Ubuntu y otra en Windows. Muchos estudiantes trabajan en Windows, y un error de rutas o de codificación solo aparece ahí.
- `fail-fast: false` deja terminar a las dos máquinas aunque una falle, así ves los dos resultados.
- `uv sync --locked` instala exactamente las versiones de `uv.lock`. Si alguien cambió `pyproject.toml` sin actualizar el lock, este paso falla.

Los otros dos jobs empiezan solo si `test` pasó (`needs: test`):

- `quality-gate` ejecuta las pruebas lentas del flujo (`tests/integration/test_flows.py`), que entrenan un modelo, lo registran, lo promueven con el gate y corren seis meses del ciclo mensual.
- `docker` construye la imagen de la guía 04, la arranca sin MLflow y comprueba que `/health` responde 200 y `/ready` responde 503.

## Paso 2. Corre los mismos chequeos en tu máquina

Antes de subir algo, puedes correr lo mismo que el job `test`:

```bash
uv run ruff check
```

```text
All checks passed!
```

```bash
uv run ruff format --check
```

```text
80 files already formatted
```

Ruff también revisa el código dentro de los archivos Markdown, así que el número crece con cada guía nueva.

```bash
uv run pytest
```

```text
...
====================== 172 passed, 8 deselected in 27.24s ======================
```

(salida recortada). Las 8 pruebas `deselected` son las lentas (`@pytest.mark.slow`), que `pyproject.toml` excluye por defecto. El tiempo cambia en tu máquina.

Para no olvidarte de `ruff`, instala el hook de pre-commit. Desde ese momento, cada `git commit` ejecuta `ruff` sobre los archivos que cambiaste:

```bash
uv run pre-commit install
```

```text
pre-commit installed at .git/hooks/pre-commit
```

## Paso 3. Rompe una prueba en una rama

Crea una rama:

```bash
git switch -c demo/ci-rojo
```

Abre `tests/test_schema.py` con tu editor y agrega al final una prueba que fija el ingreso mínimo del contrato de datos, el límite que atrapó el bug de unidades en la guía 02. Equivócate a propósito y escribe 5000 en vez de 500. Deja dos líneas en blanco antes del `def`, como pide el formato de ruff.

```python
def test_income_floor() -> None:
    assert NUMERIC_FEATURES["monthly_income_pen"].min == 5000
```

Guarda el archivo y haz commit sin correr las pruebas, como haría alguien con prisa:

```bash
git add tests/test_schema.py
git commit -m "test: pin the income floor of the data contract"
```

```text
ruff check...............................................................Passed
ruff format..............................................................Passed
check for added large files..............................................Passed
[demo/ci-rojo 9badede] test: pin the income floor of the data contract
 1 file changed, 4 insertions(+)
```

Pre-commit pasa, porque el código tiene buen formato. `ruff` revisa el estilo, no si la prueba es correcta. La primera vez, pre-commit descarga sus entornos y tarda más. Esta salida es de un ensayo aparte del instructor, por eso su SHA no coincide con el del push de abajo. En tu máquina los SHA serán otros.

Sube la rama:

```bash
git push -u origin demo/ci-rojo
```

```text
remote:
remote: Create a pull request for 'demo/ci-rojo' on GitHub by visiting:
remote:      https://github.com/AHuaman/demo-mlops/pull/new/demo/ci-rojo
remote:
To https://github.com/AHuaman/demo-mlops.git
 * [new branch]      demo/ci-rojo -> demo/ci-rojo
branch 'demo/ci-rojo' set up to track 'origin/demo/ci-rojo'.
```

Abre el enlace que imprime `git push` (con tu usuario y tu repositorio). GitHub te muestra el formulario del pull request hacia `main`. Pulsa **Create pull request**.

## Paso 5. Arregla y mira el verde

En `tests/test_schema.py`, cambia `5000` por `500`. Comprueba en tu máquina:

```bash
uv run pytest tests/test_schema.py
```

```text

```

(salida recortada). Haz commit y sube:

git add tests/test_schema.py

En este ejercicio la prueba repite lo que ya cubren las pruebas del contrato (`tests/data/test_contract.py`), así que ciérralo sin fusionar con el botón **Close pull request** y luego pulsa **Delete branch**. En tu máquina, vuelve a `main` y borra la rama:

```bash
git switch main
git branch -D demo/ci-rojo
```

```text

Deleted branch demo/ci-rojo (was 69bb5c4).
```

`-D` (en mayúscula) borra la rama aunque nunca se haya fusionado.

## Por qué así

**GitHub Actions.** Viene con cada repositorio de GitHub y no necesita un servidor propio. El workflow es un archivo del repositorio, así que cambia con el código y se revisa en el mismo pull request.

**Ubuntu y Windows.** Las pruebas pasan en tu laptop y pueden fallar en la de tu compañero. La matriz las corre en los dos sistemas que usa el curso. El job de Windows es el más lento. En las corridas del instructor tardó entre 5 y 7 minutos, contra un minuto y medio de Ubuntu.

**`uv sync --locked`.** CI instala las mismas versiones que tú, las de `uv.lock`. Un "en mi máquina funciona" por versiones distintas no llega a `main`.

**Pre-commit y CI.** Pre-commit corre en tu máquina y responde en segundos, pero lo puedes saltar (`git commit --no-verify`) o no tenerlo instalado. CI corre siempre, en una máquina limpia. Los dos ejecutan `ruff`, y solo CI ejecuta las pruebas.

**Un check rojo bloquea el merge solo si lo exiges.** Como explica el primer de CI/CD, el bloqueo necesita una regla de protección de rama, que en un repositorio privado requiere un plan de pago. Sin la regla, la norma del equipo no cambia. No se fusiona con CI en rojo.

## Si algo falla

**No aparece ningún check en el pull request.** Revisa la pestaña **Actions** de tu repositorio. Si GitHub muestra un aviso para habilitar los workflows, acéptalo y vuelve a subir un commit. Si el workflow sí está habilitado, espera. En la preparación del repositorio, GitHub tardó unos 5 minutos en empezar la primera corrida después del push.

**El job de Windows sigue corriendo cuando Ubuntu ya terminó.** Es normal. Para este ejercicio basta con ver el resultado de Ubuntu. El de Windows llega unos minutos después.

**`git push` pide usuario y contraseña.** GitHub no acepta tu contraseña por HTTPS. Usa un token personal o inicia sesión con Git Credential Manager (viene con Git para Windows). Si clonaste con la URL de otra persona, el push falla con un error de permisos. Clona tu propio repositorio.
